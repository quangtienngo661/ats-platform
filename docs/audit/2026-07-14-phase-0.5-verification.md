## 2. Kết quả verify chi tiết (bằng chứng quan sát trực tiếp)

### Nhóm 1 — Bảo mật (100% PASS)

- Candidate gửi `{"userInfo":{"role":"admin"}}` → **400**, DB xác nhận `role` không đổi.
- Token cấp **trước khi** khoá tài khoản → dùng lại → **401** ngay (trước đây token cũ vẫn dùng được tới khi hết hạn).
- `GET /job-postings?status=draft`: không token và **cả token candidate** → không thấy tin nháp nào; token recruiter/admin → thấy đúng.
- `POST /auth/reset-password` gọi 8 lần liên tiếp → **429** đúng từ lần thứ 6.
- Swagger: có ở dev, **không mount** khi `NODE_ENV=production`.

### Nhóm 2 — Độ tin cậy bất đồng bộ

- **Đường thành công (lần đầu tiên verify được, nhờ key Gemini mới):** upload CV thật → `cvs.parsing_status = completed`, `cv_parsed_data` có nội dung Gemini trích xuất thật (ví dụ: *"Backend engineer with 2 years experience in Node.js, NestJS, and PostgreSQL"*). Chấm điểm CV thật → `cv_screenings.status = completed`, có `overall_score` + `ai_reasoning` bằng tiếng Việt thật do Gemini sinh ra.
- **Đường thất bại + retry (bằng chứng từ lượt verify trước đó dùng key cũ hết hạn mức, vẫn hợp lệ):** upload CV với key lỗi → log cho thấy **3 lần thử**, cách nhau ~10s rồi ~20s (đúng backoff luỹ thừa, base 10s) → `parsing_status = failed`.
- **Trần retry:** screening đã `failed` với `retry_count = 3` → gọi lại `POST /applications/:id/trigger-screening` → **409** *"Sàng lọc AI đã thất bại 3 lần. Vui lòng kiểm tra lại CV hoặc liên hệ quản trị viên"*.
- **Rate limit qua Redis:** 6 lần login sai → 429 ở lần 6; `docker exec ats-redis redis-cli KEYS "throttle:*"` thấy key thật; **restart container `ats-api` xong, gọi login ngay lập tức vẫn 429** — chứng minh bộ đếm sống trong Redis, không mất khi restart (trước đây nằm trong RAM, restart là reset).
- **Job quét phiên phỏng vấn treo — PASS (bổ sung 2026-07-14 21:20 UTC+7):** một tiến trình theo dõi chạy nền từ trước đã ghi lại được lần quét thật. Log xác nhận: `[InterviewSessionService] Session verify-test-session-001 abandoned after inactivity` và `[InterviewAbandonProcessor] Swept 1 stale interview session(s): verify-test-session-001`. Đọc lại DB xác nhận `status = abandon`. Kịch bản §4.1 không còn cần thiết, giữ lại để tham khảo cách tái tạo.

### Nhóm 3 — Toàn vẹn nghiệp vụ (100% PASS, verify trực tiếp)

- `isReverted: true` revert sang trạng thái đơn **chưa từng đi qua** (`applied` không có lịch sử → revert sang `hired`) → **400**: *"Không thể hoàn tác về trạng thái 'hired' vì đơn ứng tuyển chưa từng ở trạng thái này. Các trạng thái có thể hoàn tác: [applied]"*.
- Đơn đã đi `applied→screening→interview→offer`, revert `offer→interview` (hợp lệ vì đã từng ở `interview`) → **200**, và **có notification thật được tạo** (trước đây nhánh revert return sớm, không bao giờ gọi tới bước tạo notification).
- Tin tuyển dụng `active`→`closed`→ thử mở lại → **400**: *"Các trạng thái hợp lệ: [không có - đây là trạng thái cuối]"*.
- Resave tin đang `active` (không đổi status) → `published_at` **không đổi**.
- Lịch phỏng vấn `completed` → thử chuyển lại `scheduled` → **400**.
- Xoá phòng ban còn recruiter → **400** *"còn nhà tuyển dụng"*. Xoá skill đang gắn tin → **400** *"đang được sử dụng"*. Xoá user (candidate) đang có đơn ứng tuyển → **400** *"đã có đơn ứng tuyển"*. Tạo skill trùng tên khác category → **400** *"đã tồn tại"* (không phải lỗi 500 thô).

### Nhóm 4 — Vận hành

- `GET /health` khi mọi thứ bình thường → **200**, `{"database":"up","redis":"up"}`.
- **Phát hiện thật, chưa sửa (đúng quy tắc verify — chỉ báo cáo, không tự vá):** khi Redis bị đóng băng hoàn toàn (`docker pause`, mô phỏng treo mạng thay vì tắt hẳn), health check **treo luôn, không trả về 503**. Nguyên nhân: `HealthService` gọi `redis.ping()` không có giới hạn thời gian chờ (timeout). Đây khác với "Redis tắt hẳn" (sẽ báo lỗi kết nối ngay) — đây là ca "Redis còn đó nhưng không phản hồi", ít gặp hơn nhưng có thật (ví dụ Redis quá tải). **Khuyến nghị sửa ở đợt sau:** bọc `Promise.race` với timeout ~2-3s quanh cả 2 lệnh ping trong `apps/api/src/app/health/health.service.ts`.
- Graceful shutdown: chưa quan sát được log rõ ràng do bị dừng giữa chừng lúc test — kịch bản để bạn tự chạy ở §4.

## 4. Kịch bản để bạn tự chạy nốt

Yêu cầu: `ats-api`, `ats-postgres`, `ats-redis` đang chạy (`docker-compose -f docker-compose-dev.yml up -d`), container `ats-api` đã build từ code mới nhất (`docker-compose -f docker-compose-dev.yml up -d --build api`).

### 4.1. Job quét phiên phỏng vấn treo (Nhóm 2, mục còn thiếu)

Không restart `ats-api` trong lúc chờ — mỗi lần restart tính lại đồng hồ 5 phút từ đầu.

```bash
# 1. Xác nhận scheduler đã đăng ký
docker exec ats-redis redis-cli KEYS "bull:interview-maintenance:*"
# phải thấy: bull:interview-maintenance:repeat:interview-stale-sweep...

# 2. Chèn một phiên phỏng vấn "treo" giả lập (đã tồn tại sẵn từ lượt verify này, tái dùng luôn):
docker exec ats-postgres psql -U postgres -d ats-db -c \
  "SELECT session_id, status, started_at FROM interview_sessions WHERE session_id='verify-test-session-001';"
# Nếu không còn, tạo mới (thay candidate_id/topic_id/difficulty_level cho đúng dữ liệu thật):
#   INSERT INTO interview_sessions (session_id, candidate_id, topic_id, difficulty_level, status, started_at)
#   VALUES ('verify-test-session-001', '<candidate_id có thật>', '<topic_id có thật>', 'medium', 'in_progress', now() - interval '1 hour');

# 3. Đảm bảo không có dấu hoạt động trong Redis cho phiên này
docker exec ats-redis redis-cli GET "interview:activity:verify-test-session-001"
# phải trả về (nil)

# 4. Chờ tối đa 5 phút (không đụng container), rồi kiểm tra:
docker exec ats-postgres psql -U postgres -d ats-db -t -c \
  "SELECT status FROM interview_sessions WHERE session_id='verify-test-session-001';"
# PASS nếu trả về "abandon"

# 5. Xem log xác nhận:
docker logs ats-api --since 10m | grep -i "abandoned after inactivity"
```

### 4.2. Graceful shutdown (Nhóm 4, mục còn thiếu)

```bash

docker logs -f ats-api

# Ở terminal khác, restart:

# Trong log vừa mở, tìm các dòng đóng kết nối TRƯỚC dòng "Application is running on"

# KHÔNG PASS nếu tiến trình cũ biến mất đột ngột không có log dọn dẹp.
```

### 4.3. (Tuỳ chọn) Sửa lỗi health-check treo khi Redis đơ

Không bắt buộc cho Phase 0.5, nhưng nên làm trước khi dùng health check này cho việc tự động giám sát:

```ts
// apps/api/src/app/health/health.service.ts — bọc timeout quanh redis.ping()
const withTimeout = <T>(promise: Promise<T>, ms: number) =>
  Promise.race([
    promise,
    new Promise<never>((_, reject) => setTimeout(() => reject(new Error('timeout')), ms)),
  ]);

// trong checkRedis(): await withTimeout(this.redis.ping(), 3000)
```
