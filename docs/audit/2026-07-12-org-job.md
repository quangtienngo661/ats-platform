## Underused/dead DB fields

### User.phoneNumber — accepted by DTO, never persisted
`CreateUserDto`/`UpdateUserDto` (`apps/api/src/app/users/dtos/user.dto.ts:29-35`) declare `phoneNumber` as a valid, whitelisted field, and `UserDto.fromEntity` reads it back out (`user.dto.ts:123`). But neither write path in `users.service.ts` ever includes it in the Prisma `data` object:

- `create()` — `apps/api/src/app/users/users.service.ts:24-32`:
  ```
  data: {
    email: data.email,
    passwordHash,
    fullName: data.fullName,
    status: data.status ?? UserStatus.active,
    role: data.role,
    emailVerified: true
  },
  ```
  no `phoneNumber`.
- `update()` — `users.service.ts:136-142`:
  ```
  data: {
    email: updateUserDto.email,
    passwordHash,
    fullName: updateUserDto.fullName,
    status: updateUserDto.status,
    role: updateUserDto.role,
  },
  ```
  no `phoneNumber`.

Result: a client can submit `phoneNumber` on `POST /users` or `PATCH /users/:id` (and it passes validation, since it's declared on the DTO), but the value is silently dropped — the column stays `null` forever via these code paths. It IS read elsewhere (e.g. `candidates.service.ts:134`, `:175`, `:210` select and search on `user.phoneNumber`), so it's not fully dead, but it is **write-only-in-appearance / actually unwritable** through the admin user CRUD endpoints. (Candidates can set it only via the `userInfo` passthrough described in the Business logic gaps section below — which is itself a bug.)

### Skill.synonyms — schema field, zero application code touches it
`grep -r "synonyms" apps/api/src` returns no matches. Not in `CreateSkillDto`/`UpdateSkillDto` (`apps/api/src/app/skills/dtos/skills.dto.ts`), not selected/omitted explicitly anywhere (it comes back incidentally whenever `skill: true` is included, e.g. `jobPostingIncludeOptions` in `apps/api/src/common/utils/include-options.util.ts:18-21`, but nothing ever sets it or reads it for logic). Confirmed orphaned — no create/update endpoint exposes it, no matching/search logic consumes it.

### JobPosting.departmentId — accepted in `CreateJobPostingDto` but silently ignored
`CreateJobPostingDto.departmentId` (`apps/api/src/app/job-postings/dto/job-posting.dto.ts:62-69`) is a declared, validated (`@IsUUID()`) field, but `JobPostingsService.create()` never reads `createJobPostingDto.departmentId` — it always derives the department from the calling recruiter's own `recruiter.departmentId` (`job-postings.service.ts:70-79`, `109-111`). Not a security hole (client can't fake it), but it's a dead/misleading DTO field — Swagger documents it as settable when it never is.

### CreateJobPostingDto.createdBy — accepted but ignored on create, dangerous on update
Same DTO field, opposite problem on the other endpoint — see "JobPosting.recruiter / createdBy reassignment" in Business logic gaps below. On `create()` it's ignored entirely (`job-postings.service.ts:39-135` never reads `createJobPostingDto.createdBy`); on `update()` it's read and directly trusted (`job-postings.service.ts:222-226`).

### CreateJobPostingDto.publishedAt — accepted by DTO, always overwritten server-side
`job-posting.dto.ts:161-167` declares a client-settable `publishedAt`. Both `create()` (`job-postings.service.ts:106-108`) and `update()` (`:214-216`) always compute `publishedAt` themselves from `status === JobStatus.active ? new Date() : undefined` and never reference `createJobPostingDto.publishedAt`/`updateJobPostingDto.publishedAt`. Whatever the client sends for this field is discarded. (Arguably correct behavior — but the DTO/Swagger doc is misleading, and worth simplifying by removing the field from the DTO if it's never meant to be client-supplied.)

### JobPostingSkillsService.deleteBySkillId — dead method
`apps/api/src/app/job-postings/job-posting-skills/job-posting-skills.service.ts:24-28` defines `deleteBySkillId(skillId, tx?)`. `grep -r "deleteBySkillId" apps/api/src` finds only the definition — no caller anywhere in the app. In particular, `SkillsService.remove()` (`apps/api/src/app/skills/skills.service.ts:90-102`) does **not** call it before deleting a skill (see the FK-violation gap in Business logic gaps below) — the helper that would have made that safe exists but was never wired up.

## Business logic gaps

### 1. CRITICAL — Candidate can self-escalate to admin via `PATCH /candidates/me` (`userInfo` passthrough)
`UpdateCandidateProfileDto.userInfo` is typed as the plain interface `IUserDto` and validated only with `@IsObject()` (`apps/api/src/app/candidates/dtos/candidates.dto.ts:35-37`):
```
@IsOptional()
@IsObject()
userInfo: IUserDto;
```
No `@ValidateNested()` + `@Type(() => SomeClass)`. The global `ValidationPipe` in `apps/api/src/main.ts:69-71` runs with `whitelist: true, forbidNonWhitelisted: true` — but `whitelist` only strips/rejects properties that aren't declared on the DTO **class it's validating**; since `userInfo`'s value is a raw plain object (no nested class-validator metadata), none of its inner keys are stripped or validated.

`CandidatesService.updateProfile()` then spreads that raw object directly into a Prisma nested `user.update`:
```
// apps/api/src/app/candidates/candidates.service.ts:59-63
user: {
  update: {
    ...updateDto.userInfo
  }
}
```
`PATCH /candidates/me` is reachable by any authenticated user with role `candidate` (`apps/api/src/app/candidates/candidates.controller.ts:27-37`, `@Roles(UserRole.candidate)`). A request body of:
```json
{ "userInfo": { "role": "admin" } }
```
passes validation (`userInfo` is a whitelisted top-level property) and is passed straight to `prisma.user.update({ data: { role: "admin", ... } })` for the candidate's own `User` row. Same applies to `status`, `emailVerified`, `email`, and (if the plaintext key happens to match the column name) any other `User` scalar. This is a full privilege-escalation path — a candidate becomes an admin on their own account with a single API call, then needs only to log in again (or hit `/auth/refresh`) to get a JWT carrying `role: admin` (confirmed `AuthService.login()` reads `role` fresh from the DB at `auth.service.ts:122`).

Fix direction: either drop `userInfo` from this DTO entirely (candidates don't need to touch `User` fields other than maybe `fullName`/`phoneNumber`), or replace it with an explicit whitelisted sub-DTO (`@ValidateNested() @Type(() => CandidateUserInfoDto)`) containing only `fullName`/`phoneNumber`.

### 2. `UserStatus.inactive` is set by admins but never enforced at login
`UsersService.update()` lets an admin set `status: UserStatus.inactive` on a `User` (`apps/api/src/app/users/dtos/user.dto.ts:37-44`, `users.service.ts:94-154`). But `AuthService.login()` (`apps/api/src/app/auth/auth.service.ts:99-136`) only checks password validity and `user.emailVerified` — it never checks `user.status`:
```
// auth.service.ts:104-120
const user = await this.prisma.user.findUnique({ where: { email: loginDto.email } });
...
const isPasswordValid = bcrypt.compareSync(loginDto.password, user.passwordHash);
...
if (!user.emailVerified) { throw new BadRequestException('EMAIL_NOT_VERIFIED:' + user.email); }
// no status check here — issues tokens regardless of status
```
`JwtStrategy.validate()` (`apps/api/src/app/auth/strategies/jwt.strategy.ts:28-30`) and `AuthService.refreshToken()` (`auth.service.ts:263-341`) also never re-check `status` against the DB — they trust whatever `role`/claims are baked into the JWT. Net effect: "deactivating" a user via the admin panel has zero effect on that user's ability to log in or keep using an already-issued/refreshed session. `UserStatus` is effectively a decorative field for the auth flow.

### 3. Deleting a Department/User/Skill with existing dependents throws an unhandled FK error instead of a friendly message
Several `*.remove()` methods delete a parent row without checking for children that the schema does **not** cascade-delete (no `onDelete: Cascade` on the child's FK to that parent → Postgres/Prisma default is Restrict/NoAction):

- `DepartmentsService.remove()` (`apps/api/src/app/departments/departments.service.ts:69-83`) deletes a `Department` with no check for existing `Recruiter`s or `JobPosting`s. Both `Recruiter.department` (`schema.prisma:246-247`) and `JobPosting.department` (`schema.prisma:297`) relations have no `onDelete` clause → Restrict. A department with any recruiter or job posting attached will throw a raw Prisma `P2003` that isn't caught (only `NotFoundException` is handled), surfacing as an unhandled 500 instead of `'Không thể xóa phòng ban còn nhà tuyển dụng/tin tuyển dụng'`. Compare with `JobCategoriesService.remove()` (`job-categories.service.ts:89-112`), which correctly guards against `childCategories` before deleting — the same pattern is missing here.
- `UsersService.remove()` (`apps/api/src/app/users/users.service.ts:156-168`) deletes a `User` directly. `Candidate.user` and `Recruiter.user` both cascade (`schema.prisma:227`, `246`), so those child rows do get removed — but that cascade then hits further Restrict-only relations one level down: `JobPosting.recruiter` (`schema.prisma:299`, no `onDelete`) and `Application.candidate` (`schema.prisma:372`, no `onDelete`). Deleting a `User` who is a recruiter with existing job postings, or a candidate with existing applications, will fail the cascade mid-transaction with an unhandled `P2003` — the `catch` block only maps `P2025`→404 (`users.service.ts:162-167`), so this surfaces as a raw 500.
- `SkillsService.remove()` (`apps/api/src/app/skills/skills.service.ts:90-102`) deletes a `Skill` with no check for `JobPostingSkill` rows referencing it. `JobPostingSkill.skill` (`schema.prisma:313`) has no `onDelete` → Restrict. Deleting a skill still attached to any job posting throws an unhandled `P2003`. Note `JobPostingSkillsService.deleteBySkillId()` exists (`job-posting-skills.service.ts:24-28`) apparently for exactly this purpose but is never called (see dead-field section above) — the fix was half-built and never wired in.
- `RecruitersService.remove()` (`apps/api/src/app/recruiters/recruiters.service.ts:142-163`) has the same gap as the User case directly: deletes a `Recruiter` with no check for existing `JobPosting`s created by them; `JobPosting.recruiter` is Restrict, so an unhandled `P2003` results.

### 4. `JobStatus` transitions are entirely unvalidated
`JobPostingsService.update()` (`apps/api/src/app/job-postings/job-postings.service.ts:182-244`) writes `status: updateJobPostingDto.status` directly with no state-machine check anywhere in the file:
```
// job-postings.service.ts:206-213
data: {
  ...
  status: updateJobPostingDto.status,
  publishedAt: updateJobPostingDto.status === JobStatus.active ? new Date() : undefined,
  ...
}
```
Any status→status transition is accepted: `closed` → `active` (reopening a closed job with no re-validation), `active` → `draft` (unpublishing a live job that may already have applications), `draft` → `closed` (skipping `active` entirely), or setting the same status repeatedly (each call to `active` resets `publishedAt` to `now()`, silently overwriting the original publish date). There is no `JobStatus` transition table/guard comparable to `JobCategoriesService`'s circular-parent check.

### 5. `JobPosting.recruiter` (`createdBy`) can be reassigned to any recruiter, including one in a different department, with no consistency check on `departmentId`
`UpdateJobPostingDto.createdBy` (inherited via `PartialType(CreateJobPostingDto)`, `job-posting.dto.ts:79-85`) is accepted on `PATCH /job-postings/:id`. `JobPostingsService.update()`'s only validation is that the target recruiter exists (`ensureRelationsExist`, `job-postings.service.ts:279-290`):
```
if (updateJobPostingDto.createdBy) {
  const recruiter = await this.prisma.recruiter.findUnique({
    where: { recruiterId: updateJobPostingDto.createdBy },
    select: { recruiterId: true },
  });
  if (!recruiter) { throw new NotFoundException(...); }
}
```
It never checks that the new recruiter belongs to the same department as `existingJobPosting.departmentId`, and `departmentId` itself is never updated to match (there is no `departmentId` write anywhere in `update()`, `job-postings.service.ts:203-228`). Result: after such an update, `JobPosting.departmentId` and `JobPosting.recruiter.departmentId` can permanently disagree — a job posting can end up "owned" by a recruiter in Department B while its own `departmentId` still says Department A. Since `OwnershipGuard`'s `job-posting` case (`apps/api/src/common/guards/resources.guard.ts:36-55`) only requires the caller to be the *current* recruiter owner (or admin) to call `update` at all, the job posting's original owner can hand it off to an arbitrary recruiter (any department) in one call, with no re-consent from the new owner and no department realignment.

### 6. `OwnershipGuard` for job postings is per-recruiter, not per-department — no colleague can edit a teammate's posting
`resources.guard.ts:36-55` checks `jobPosting.recruiter.userId !== userId` — i.e. only the exact creating recruiter (or an admin) may update/delete a job posting. Two recruiters in the *same* department cannot edit each other's postings at all. This directly answers the audit's prompted scenario ("can a recruiter from department A modify a job posting in department B?") — no, but the flip side is also true within a single department, which may not match the intended org model (a `Department` has multiple `Recruiter`s, implying some form of team ownership, but the code enforces individual-only ownership). Flagging as a design question, not a definite bug — worth confirming against actual product intent.

### 7. Public, unauthenticated job-posting listing/detail endpoints leak `draft` and `closed` postings
`GET /job-postings` and `GET /job-postings/:id` (`apps/api/src/app/job-postings/job-postings.controller.ts:49-62`) have **no** `@UseGuards` at all — fully public. `JobPostingsService.findAll()` (`job-postings.service.ts:137-164`) only filters by `status` if the caller explicitly passes `?status=`; with no query param, every posting regardless of status (`draft`, `active`, `closed`) is returned to anonymous callers. An unauthenticated request can also explicitly pass `?status=draft` to browse a company's unpublished job postings, or `?status=closed` for old ones. There's no default/forced filter to `active` for unauthenticated/public consumption.

### 8. `SkillsService.create()`'s duplicate-name check is broken when `category` is supplied
`schema.prisma:271-280` — `Skill.name` is the only `@unique` field (no compound `@@unique([name, category])`). But the duplicate check does:
```
// apps/api/src/app/skills/skills.service.ts:10-15
const existingSkill = await this.prisma.skill.findUnique({
  where: {
    name: createSkillDto.name,
    category: createSkillDto.category,
  },
});
```
Prisma's `findUnique` uses `name` as the actual unique lookup key and treats `category` as an additional AND-filter on top of it. If a skill named "TypeScript" already exists with `category: "Programming Language"` and a client submits `create({ name: "TypeScript", category: "Frontend" })` (different category, same name), `existingSkill` comes back `null` — the duplicate isn't detected — and the subsequent `prisma.skill.create()` call (`skills.service.ts:21-26`) throws an unhandled Prisma `P2002` unique-constraint violation (on `name`) instead of the intended `BadRequestException('Kỹ năng đã tồn tại')`. The check should look up by `name` alone.

### 9. `RecruitersService.update()` doesn't re-validate `departmentId`/`userId` on admin edits
`update()` (`apps/api/src/app/recruiters/recruiters.service.ts:118-140`) passes `updateRecruiterDto` straight through as `data` with no existence check on a changed `departmentId` or `userId`, unlike `create()` which explicitly validates both (`recruiters.service.ts:12-30`). `UpdateRecruiterDto extends PartialType(CreateRecruiterDto)` so both fields are legally patchable by an admin (`recruiters.controller.ts:76-86`, admin-only). Supplying a non-existent `departmentId` throws an unhandled FK error rather than the friendly `NotFoundException('Không tìm thấy phòng ban')` used elsewhere in this same file.

### 10. Minor — `POST /auth/reset-password` has no rate limiting
`login`, `register`, and `forgot-password` all carry `@UseGuards(ThrottlerGuard)` (`apps/api/src/app/auth/auth.controller.ts:25`, `46-47`, `101`), but `reset-password` (`auth.controller.ts:111-119`) does not. It's gated by possession of a random 32-byte token (not purely guessable), so the risk is lower than an unthrottled login, but it's the one state-changing auth endpoint in the file without any throttle, and it's adjacent to the pattern the other three already established.
