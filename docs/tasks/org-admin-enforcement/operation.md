## 2. A defect the unit suite could not see — and its fix

The first walk failed at its first step: `POST /organizations` returned **409 "Slug 'walk-org-b' đã được
sử dụng"** although no organization had that slug. Cause: `ai_configs_only_one_default_idx`, a partial
unique index from March (`20260321101500_ai_config_default_partial_unique`) allowing **one default config
in the whole system**. Creating an organization creates its own default (D8), which that index refused;
the service read the P2002 as a slug conflict. Prisma cannot express partial indexes, so the index is in
no schema file — only a migration — and every unit test mocks Prisma.

- **RED** (`results/red-one-default-per-org.txt`): a default in a second organization is rejected by
  `ai_configs_only_one_default_idx`; the control (a second default inside one organization) is rejected too.
- **Fix:** migration `20260919053000_ai_config_default_per_organization` — unique on `organization_id`
  where `is_default` (`decision.md` D11).
- **GREEN** (`results/green-one-default-per-org.txt`): the second organization's default is accepted; the
  control is still rejected, now by `ai_configs_one_default_per_organization_idx`.

## 4. Socket rooms — and why the first reading was wrong

`join_job_room` answers nothing to the client; the decision is only in the server log
(`results/socket-join-log.txt`). Two instrument problems came up before there was a real reading:

1. **Every connection refused.** The gateway's `allowRequest` admits only `Origin === CLIENT_URL`; the test
   client sent no Origin. Fixed in the client (it now sends the origin the web sends).
2. **A race that looked like enforcement.** Joining immediately on `connect`, 3 of 4 clients were refused —
   including the platform admin, who must be allowed. The log showed each refusal *before* that client's
   `joined room: user_…` line: the join arrived while the server's async handshake (JWT verify + database
   read) had not yet set `client.data.user`. Two of those refusals looked "correct" and would have been
   read as proof. Joining after the handshake, each decision follows the user-room line:

| Client | `job_<A's job>` |
|---|---|
| org_admin B | refused |
| recruiter B | refused |
| org_admin A (control) | joined |
| platform admin (control) | joined |

The race itself is **pre-existing** and real for the web too: `InitSocketRoom` joins as soon as the store
reports `connected`. Recorded as a separate defect, not fixed here.

Since 2026-09-19 the walk reads the API log itself (`docker logs ats-api --since <start>`) and fails a
socket check whose decision came before that client's handshake line — so the race can no longer pass as
a reading. Teeth, run 2026-09-19 on throwaway copies of the script: joining immediately on `connect`
→ **4 of 4** socket checks FAIL "decided before the handshake finished" (the race is real every time at
that timing); keeping the wait but expecting org_admin A to be refused → **exactly 1** FAIL, "joined,
expected refused".
